THE EXIT 127 IS EXPLAINED, AND THE EARLIER DIAGNOSIS WAS WRONG.

ffmpeg is NOT absent. It is present at /usr/bin/ffmpeg and is BROKEN: the dynamic
linker cannot find libunwind.so.8. A shared-library failure exits 127, the SAME code as
command-not-found, which is why the earlier CalledProcessError was misread as ffmpeg
missing from the compute-node PATH. It fails identically on the login node. No module
on Vista provides ffmpeg.

Correction owed: 2026-07-25_lane-R-render.md and the Mac-side memory both state that
ffmpeg is absent from gh-dev compute nodes. That wording is wrong. It is present and
unusable on both node classes. Not edited here, scope forbids it. Flagged for the next
writer.

Implication for any render task: write_mp4 will fail at the ffmpeg call every time, on
every node, until libunwind is supplied or the frames are encoded elsewhere. The PNG
frames are still produced and are unaffected; only the encode step dies. Do not spend
another cycle diagnosing this as a PATH or module problem.
