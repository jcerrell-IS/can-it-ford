# Genesis World v1.2.0 on TACC Vista GH200 via Apptainer: Issues, Limits, and Best Practices

## Executive summary

The strongest confirmed finding is that Genesis World v1.2.0 should be treated as a **Quadrants-based** simulator rather than an upstream-Taichi-based simulator: its v1.2.0 `pyproject.toml` pins `quadrants==1.0.2`, requires Python `>=3.10,<3.14`, and does not list upstream `taichi` as a dependency ([Genesis World v1.2.0 pyproject](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/pyproject.toml)). This matters for Vista because Quadrants publishes Linux ARM64/aarch64 wheels and describes support for NVIDIA CUDA plus ARM64 CPUs, while upstream Taichi’s current PyPI files show x86-64 Linux wheels and macOS ARM64 wheels but not Linux ARM64 wheels ([Quadrants PyPI files](https://pypi.org/project/quadrants/#files); [Taichi PyPI files](https://pypi.org/project/taichi/#files)).

The most relevant confirmed Genesis physics risk for a weakly-compressible water + rigid vehicle run is **MPM-rigid coupling leakage/penetration through thin or under-resolved rigid geometry**, not GH200 itself: Genesis issue #600 reports MPM particles passing through rigid bodies, and the maintainer-style response explains that MPM-rigid coupling collides through the MPM grid, so the grid should be smaller than the rigid object, with `grid_density=128` or `256` suggested and `grid_density=128` reported to “almost” resolve the issue ([Genesis issue #600](https://github.com/Genesis-Embodied-AI/genesis-world/issues/600)). Genesis v1.2.0’s MPM options directly support that mitigation because `grid_density` defaults to 64, `particle_size` is computed as `0.01 * 64 / grid_density` when omitted, and `enable_CPIC` is documented as supporting coupling with thin objects, defaulting to `False` ([Genesis v1.2.0 MPMOptions](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/options/solvers.py)).

The most relevant confirmed Vista/platform risk is not a documented Genesis-on-Vista failure but the combination of ARM64 packaging, host-bound GPU libraries in Apptainer, and GH200 unified memory behavior: Vista’s GH nodes are Grace-Hopper nodes with one H200 GPU with 96 GB HBM3 and one Grace CPU with about 116-120 GB LPDDR, while Apptainer `--nv` binds host NVIDIA devices and host CUDA libraries into the container ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/); [Apptainer GPU support](https://apptainer.org/docs/user/main/gpu.html)). The practical recommendation is to build an ARM64 Apptainer image, use `apptainer exec --nv`, install `genesis-world==1.2.0` and an aarch64 CUDA-enabled PyTorch wheel from the correct PyTorch index or TACC module workflow, keep MPM working sets under the 96 GB HBM target when possible, and validate water-rigid coupling with grid-convergence tests before trusting ford/no-ford outcomes ([PyTorch aarch64 issue #160162](https://github.com/pytorch/pytorch/issues/160162); [TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/); [NVIDIA GH200 memory blog](https://developer.nvidia.com/blog/simplify-system-memory-management-with-the-latest-nvidia-gh200-nvl2-enterprise-ra/)).

### CUDA/runtime issues that could appear inside a GH200 container

Genesis issue #2814 reports a batch-renderer CUDA linking failure, `ERROR 4 in nvvmAddNVVMContainerToProgram`, with a comment saying a CUDA 12.8 environment and PyTorch `cu128` index avoided the error on a Vast.ai instance ([Genesis issue #2814](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2814)). This issue is not a confirmed MPM solver failure, but it argues for disabling heavy/batch rendering during production L2 physics runs and validating renderer-free stepping first ([Genesis issue #2814](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2814)).

Genesis issue #2942 reports a release-version CUDA fatbin error for Blackwell `SM 120`, while a maintainer could not reproduce it on an RTX 5090 and suggested a newer driver; this is not a GH200/Hopper bug but is evidence that release fatbins, driver versions, and GPU SM targets can be a practical runtime failure mode ([Genesis issue #2942](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2942)). For Vista’s Hopper/H200 target, the actionable version of this risk is to verify `gs.init(backend=gs.gpu)` and one `scene.step()` on `gh-dev` before submitting long production jobs ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/); [Genesis issue #2942](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2942)).

Genesis issue #2890 reports a host-memory regression when loading many small textured GLB submeshes, with an 800-textured-submesh case using about 26 GiB RSS in Genesis 0.4.7/1.0.0 compared with about 1.3 GiB in 0.3.12 and about 1.2 GiB for an untextured control ([Genesis issue #2890](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2890)). This issue is not water-specific, but it can affect a vehicle simulation if the visual vehicle mesh is a complex textured GLB; using a simplified untextured collision mesh and separating visualization from physics is the safer Vista workflow ([Genesis issue #2890](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2890)).

## 3. Taichi ARM64 backend status and known issues

For Genesis World v1.2.0, upstream Taichi should be treated as a **secondary compatibility concern** rather than the primary backend, because the v1.2.0 package pins Quadrants and not upstream Taichi ([Genesis World v1.2.0 pyproject](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/pyproject.toml)). The caveat is that older examples, older Genesis installations, or project scripts may still import `gstaichi` or `taichi`, so upstream Taichi ARM64 evidence is still useful when diagnosing legacy code paths ([Genesis discussion #2071](https://github.com/Genesis-Embodied-AI/genesis-world/discussions/2071)).

Quadrants describes itself as a high-performance compiler for physics simulation that targets NVIDIA CUDA, Vulkan, Apple Metal, AMD ROCm, x86 CPUs, and ARM64 CPUs, and its PyPI files include manylinux ARM64 wheels for CPython versions such as 3.10-3.13 ([Quadrants PyPI](https://pypi.org/project/quadrants/#files)). Quadrants also states that it was forked from Taichi in June 2025, is now independent, and does not aim to maintain backward compatibility with upstream Taichi ([Quadrants PyPI](https://pypi.org/project/quadrants/#files)).

Upstream Taichi 1.7.4’s PyPI files list Windows x86-64, manylinux x86-64, and macOS ARM64 wheels, but not manylinux ARM64/aarch64 wheels, while the package requires Python `>=3.9,<4.0` ([Taichi PyPI](https://pypi.org/project/taichi/#files)). This matches Taichi GitHub issues asking for Linux aarch64 PyPI support or reporting inability to install Taichi on aarch64 and supercomputers, including issues #8369, #8756, and #8796 ([Taichi issue #8369](https://github.com/taichi-dev/taichi/issues/8369); [Taichi issue #8756](https://github.com/taichi-dev/taichi/issues/8756); [Taichi issue #8796](https://github.com/taichi-dev/taichi/issues/8796)).

Taichi source-build evidence on ARM CUDA is mixed: issue #7916 reports a Jetson Xavier AGX ARM64 build failure in the CUDA runtime module and a comment says an inline-assembly constraint change worked, while issue #8631 reports a Linux-aarch64 ARM CUDA build failure and a comment says it was fixed by PR #8654 ([Taichi issue #7916](https://github.com/taichi-dev/taichi/issues/7916); [Taichi issue #8631](https://github.com/taichi-dev/taichi/issues/8631); [Taichi PR #8654](https://github.com/taichi-dev/taichi/pull/8654)). Taichi’s developer install docs also show that ARM/Jetson builds require explicit LLVM target choices such as `ARM;NVPTX`, which reinforces that building upstream Taichi with CUDA on ARM is a compiler-stack task rather than a simple `pip install` fallback ([Taichi developer install docs](https://docs.taichi-lang.org/docs/dev_install)).

Taichi’s installation troubleshooting page documents CUDA unified-memory and preallocated-memory failure modes, including a workaround `export TI_USE_UNIFIED_MEMORY=0` for a CUDA unified-memory bus-error path and `ti.init(device_memory_fraction=...)` or `ti.init(device_memory_GB=...)` for preallocated-memory exhaustion ([Taichi install troubleshooting](https://docs.taichi-lang.org/docs/install)). This is not a confirmed Genesis v1.2.0/Quadrants setting, but it is relevant to legacy Taichi scripts or older Genesis environments that still use Taichi-style initialization ([Taichi install troubleshooting](https://docs.taichi-lang.org/docs/install); [Genesis World v1.2.0 pyproject](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/pyproject.toml)).

## 4. MPM solver stability and memory issues relevant to unified memory architectures

### Confirmed Genesis MPM solver constraints

Genesis v1.2.0’s MPM solver is grid-based: `MPMOptions` states that MPM is a hybrid Lagrangian-Eulerian method and that the Eulerian phase uses a grid representation, with `lower_bound` and `upper_bound` controlling the domain and the domain size affecting performance ([Genesis v1.2.0 MPMOptions](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/options/solvers.py)). The solver source computes `dx = 1 / grid_density`, computes grid resolution from the domain bounds, and raises an exception if the grid size exceeds `1e9`, so increasing `grid_density` must be paired with tight domain bounds around the water channel and vehicle region ([Genesis v1.2.0 MPMSolver](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py)).

Genesis v1.2.0 warns when `substep_dt` exceeds a grid-density-based suggested value, `2e-2 * dx`, with the message that the simulation might be unstable ([Genesis v1.2.0 MPMSolver](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py)). Because `substep_dt = dt / substeps` in the simulator, a water-channel run that increases `grid_density` for vehicle coupling should also reduce `dt` or increase `substeps` to keep the MPM warning quiet ([Genesis v1.2.0 Simulator](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/simulator.py); [Genesis v1.2.0 MPMSolver](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py)).

The MPM source explicitly scales particle volume by `1e3` “to avoid potential numerical instability” because actual particle volume can be very small, and it notes that mass computation must account for that scale when handling coupling ([Genesis v1.2.0 MPMSolver](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py)). This is directly relevant to weakly-compressible water + rigid vehicle coupling because the vehicle force signal depends on particle/grid mass transfer and coupling forces, not just visual water motion ([Genesis v1.2.0 MPMSolver](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py)).

Genesis v1.2.0’s hybrid rigid-soft coupling source contains an internal note on rigid-to-soft coupling: “this may lead to unstable feedback loop” ([Genesis v1.2.0 HybridEntity](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/entities/hybrid_entity.py)). This does not prove that an open-channel vehicle-water run will be unstable, but it is a source-level warning that two-way rigid/soft feedback deserves time-step and resolution validation ([Genesis v1.2.0 HybridEntity](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/entities/hybrid_entity.py)).

### Confirmed performance and memory observations

Genesis issue #412 reports low FPS in a fluid + rigid-body test and a maintainer explains that Genesis uses a MuJoCo-style constraint formulation with global solvers, making complexity quadratic with degrees of freedom, whereas PhysX uses local solvers; the same comment also warns that default particle density can be expensive and that SPH is computationally heavier than PhysX’s PBD fluid ([Genesis issue #412](https://github.com/Genesis-Embodied-AI/genesis-world/issues/412)). This issue is SPH-oriented rather than MPM-specific, but it is relevant to water + vehicle planning because it shows that fluid-particle count, substeps, and rigid-body DOFs can dominate runtime even before GH200 memory behavior becomes the bottleneck ([Genesis issue #412](https://github.com/Genesis-Embodied-AI/genesis-world/issues/412)).

Genesis issue #2890’s GLB host-memory regression is relevant to Vista because each GH node has finite CPU LPDDR as well as finite HBM, and the visual mesh path can consume tens of GiB before the MPM water grid and particle arrays are considered ([Genesis issue #2890](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2890); [TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)). For a vehicle-fording run, the safer pattern is to use a simplified collision mesh for physics, avoid hundreds of textured submeshes, and render only after the physics signal is validated ([Genesis issue #2890](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2890)).

### Unified memory: directly confirmed architecture, inferred Genesis risk

TACC describes Vista as a Grace Hopper system where the Grace Hopper Superchip combines CPU and GPU in one module, connects them with NVLINK, exposes CPU and GPU memory as separate NUMA nodes, and allows CPU or GPU memory to be accessed from either device ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)). TACC’s GH specification states that each GH node has one NVIDIA H200 GPU with 96 GB HBM3 and one Grace CPU with roughly 116-120 GB LPDDR memory ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)).

NVIDIA describes GH200 as using memory-coherent NVLink-C2C with up to 900 GB/s bandwidth and a unified virtual memory model that allows CPU and GPU threads to access CPU-resident and GPU-resident memory in a single address space, including oversubscription and on-demand paging scenarios ([NVIDIA GH200 memory blog](https://developer.nvidia.com/blog/simplify-system-memory-management-with-the-latest-nvidia-gh200-nvl2-enterprise-ra/)). NVIDIA forum guidance on Grace Hopper warns that relying only on page faults can fetch pages one 8 KB page at a time, and recommends prefetching for structured access patterns because on-demand migration will not beat explicit bulk movement for large contiguous regions ([NVIDIA Developer Forum: Grace Hopper unified memory performance](https://forums.developer.nvidia.com/t/performance-decrease-on-unified-gracehopperc/322208)).

**Inference, not confirmed Genesis bug:** if a large MPM water grid, particle arrays, visual assets, and PyTorch tensors oversubscribe HBM or migrate repeatedly between LPDDR and HBM, the run may degrade through UVM page migration rather than fail with a clean out-of-memory error ([NVIDIA GH200 memory blog](https://developer.nvidia.com/blog/simplify-system-memory-management-with-the-latest-nvidia-gh200-nvl2-enterprise-ra/); [NVIDIA Developer Forum: Grace Hopper unified memory performance](https://forums.developer.nvidia.com/t/performance-decrease-on-unified-gracehopperc/322208)). No collected source confirms a Genesis-specific GH200 UVM page-fault bug, so this should be treated as a profiling hypothesis to test with `nvidia-smi`, Nsight Systems/Compute if available, and progressively larger MPM domains on `gh-dev` ([NVIDIA Developer Forum: Grace Hopper unified memory performance](https://forums.developer.nvidia.com/t/performance-decrease-on-unified-gracehopperc/322208); [TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)).

## 5. TACC/Vista-specific guidance found

Vista is TACC’s AI-focused supercomputer and “marks a departure from the x86-based architecture” to ARM CPUs based on NVIDIA Grace Hopper technology ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)). Vista’s GH subsystem has 600 Grace-Hopper nodes, and each GH node has one H200 GPU with 96 GB HBM3 and a Grace CPU with about 116-120 GB LPDDR and 72 cores ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)).

Vista’s production queue table lists `gh` as the Grace/Hopper queue with a 64-node maximum and 48-hour maximum duration, while `gh-dev` is the Grace Hopper development queue with an 8-node maximum and 2-hour maximum duration ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)). TACC warns that jobs must not request or exclude specific compute nodes through batch scripts, `idev`, or MPI hostfiles without prior approval, and jobs that do so will be deleted from the queue ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)).

TACC’s Vista machine-learning example uses an interactive development allocation with `idev -p gh-dev -N 1 -n 1 -t 1:00:00`, loads compiler/CUDA/Python modules, and tests PyTorch with `torch.cuda.is_available()` ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)). TACC’s local PyTorch example uses `gcc/15.1.0`, `python3/3.11.8`, a venv, and installs PyTorch from the `cu129` wheel index (`https://download.pytorch.org/whl/cu129`) ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)).

The TACC documentation overview mentions a Containers at TACC workshop for Docker and Singularity/Apptainer best practices, but the collected TACC docs did not contain a Genesis-, Taichi-, or MPM-specific Vista recipe ([TACC technical documentation overview](https://docs.tacc.utexas.edu/)). Apptainer’s GPU documentation says `--nv` exposes NVIDIA devices, binds host NVIDIA/CUDA libraries into the container so they match the host driver, and sets the container library path for CUDA execution ([Apptainer GPU support](https://apptainer.org/docs/user/main/gpu.html)).

Apptainer’s GPU documentation also warns that host-library binding can create libc compatibility problems if the container libc and host libc are too far apart, and it recommends ensuring that applications were compiled for a CUDA version and device capability supported by the host driver/card ([Apptainer GPU support](https://apptainer.org/docs/user/main/gpu.html)). For Vista, that means the Apptainer image should be ARM64/aarch64 and reasonably modern, and CUDA/PyTorch/Quadrants should be validated inside an allocated GH node rather than only on a login node ([Apptainer GPU support](https://apptainer.org/docs/user/main/gpu.html); [TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)).

PyTorch is a likely ARM64 dependency pitfall: a PyTorch issue states that before PyTorch 2.8, `pip install torch` on aarch64 could install a CPU version unless users selected the CUDA wheel index, and the workaround in that issue is to install from `https://download.pytorch.org/whl/cu128` ([PyTorch issue #160162](https://github.com/pytorch/pytorch/issues/160162)). A PyTorch forum discussion similarly states that Linux aarch64 CUDA binaries are available through PyTorch’s CUDA wheel indexes and gives a `pip install torch --index-url https://download.pytorch.org/whl/cu124` example for Grace Hopper ([PyTorch forum: Conda/PyTorch CUDA 12 for ARM64 and Grace Hopper](https://discuss.pytorch.org/t/conda-pytorch-cuda-12-for-arm64-and-grace-hopper/203285)).

## 6. Water-rigid body MPM coupling specific bugs and limitations

### Confirmed MPM-rigid penetration/leakage reports

Genesis issue #600 is the clearest directly relevant bug report: the user reports granular MPM particles passing through a rigid body even though the equivalent SPH setup works, and the response explains that MPM-rigid coupling uses the MPM grid while SPH-rigid coupling uses particles directly ([Genesis issue #600](https://github.com/Genesis-Embodied-AI/genesis-world/issues/600)). The same response says the MPM grid should be smaller than the rigid object, suggests increasing `grid_density` to 128 or 256 and scaling up the rigid object, and the user reports that `grid_density=128` almost resolved the pass-through issue ([Genesis issue #600](https://github.com/Genesis-Embodied-AI/genesis-world/issues/600)). This directly affects a weakly-compressible water + rigid vehicle simulation because tires, underbody edges, body panels, and road/vehicle gaps can be thin relative to a 64 cells/m MPM grid ([Genesis issue #600](https://github.com/Genesis-Embodied-AI/genesis-world/issues/600); [Genesis v1.2.0 MPMOptions](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/options/solvers.py)).

Genesis discussion #2071 reports MPM particles inside a 6 mm diameter, 1 mm-thick Y-shaped pipe passing through the pipe and falling downward, even with `needs_coup=True`, `coup_friction=0.8`, `coup_softness=0.0001`, and `sdf_cell_size=5e-5` in the rigid material ([Genesis discussion #2071](https://github.com/Genesis-Embodied-AI/genesis-world/discussions/2071)). This is directly relevant because it shows that thin rigid boundaries can fail even when coupling flags and SDF resolution are explicitly configured ([Genesis discussion #2071](https://github.com/Genesis-Embodied-AI/genesis-world/discussions/2071)).

Genesis discussion #1291 reports a moving rigid cylinder not colliding with MPM material, while the same MPM material interacted when the cylinder fell from above, and another user reported the same question without a posted solution ([Genesis discussion #1291](https://github.com/Genesis-Embodied-AI/genesis-world/discussions/1291)). This is directly relevant to a vehicle moving laterally through water because the project’s signal is persistent lateral drag from moving vehicle-water interaction, not just particles settling onto a static object ([Genesis discussion #1291](https://github.com/Genesis-Embodied-AI/genesis-world/discussions/1291)).

Genesis issue #2319 reports unrealistic liquid interaction with a rigid container: liquid does not leak when the container is close to the ground but seeps out when the container is suspended, and the issue remained open in the collected evidence after a maintainer requested a standalone reproduction and noted missing files ([Genesis issue #2319](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2319)). This is directly relevant as a fluid-rigid leakage warning, although the issue describes a container scenario rather than an open-channel vehicle fording scenario ([Genesis issue #2319](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2319)).

### Confirmed limitations around batching, differentiability, and contacts

Genesis discussion #1485 reports a build error for an MPM-based scene with `n_envs=2`: “Batching is only supported for rigid-only scenes as of now,” and the maintainer’s reply was to update to the latest Genesis version ([Genesis discussion #1485](https://github.com/Genesis-Embodied-AI/genesis-world/discussions/1485)). Because the project targets v1.2.0, batching should be smoke-tested before assuming many parallel MPM water-vehicle environments are available on a single GH node ([Genesis discussion #1485](https://github.com/Genesis-Embodied-AI/genesis-world/discussions/1485); [Genesis World v1.2.0 pyproject](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/pyproject.toml)).

Genesis issue #2865 reports that GPU split narrowphase with `requires_grad=True` skipped GJK in a convex-convex contact path, producing zero contacts and objects passing through each other, while the same scene with `requires_grad=False` produced contacts normally ([Genesis issue #2865](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2865)). This issue is rigid-contact/differentiability-specific rather than MPM-water-specific, but it supports using forward-only `requires_grad=False` for ford/no-ford production runs unless differentiable gradients are explicitly needed ([Genesis issue #2865](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2865)).

Genesis issue #2815 reports a possible non-returning GPU kernel in the rigid-body MPR collision path, with the reporter saying a rare non-deterministic hang made `scene.step()` stop returning during GPU rigid-body simulation and that adding a finite loop locally stopped the hang in reproduction runs ([Genesis issue #2815](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2815)). This is not an MPM-water bug, but it matters for a detailed rigid vehicle with convex collision pieces because a ford simulation can still fail in the rigid narrow-phase solver ([Genesis issue #2815](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2815)).

## 7. Practical recommendations for running v1.2.0 in Apptainer on GH200

### Build and dependency recommendations

1. Use an **ARM64/aarch64 Apptainer image**, not an x86-64 image, because Vista GH nodes and login nodes are ARM-based Grace systems ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)).
2. Install `genesis-world==1.2.0` and verify that `quadrants==1.0.2` is installed, because v1.2.0 pins Quadrants and not upstream Taichi ([Genesis World v1.2.0 pyproject](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/pyproject.toml)).
3. Do not install upstream `taichi` into the Genesis v1.2.0 container unless a separate legacy script requires it, because Taichi PyPI currently lacks Linux ARM64 wheels while Quadrants publishes Linux ARM64 wheels ([Taichi PyPI files](https://pypi.org/project/taichi/#files); [Quadrants PyPI files](https://pypi.org/project/quadrants/#files)).
4. Install CUDA-enabled aarch64 PyTorch from the appropriate PyTorch CUDA wheel index or TACC’s documented Vista workflow, because PyTorch aarch64 CUDA wheel selection has historically required explicit indexes and TACC documents a `cu129` install workflow on Vista ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/); [PyTorch issue #160162](https://github.com/pytorch/pytorch/issues/160162); [PyTorch forum: ARM64 Grace Hopper](https://discuss.pytorch.org/t/conda-pytorch-cuda-12-for-arm64-and-grace-hopper/203285)).
5. Prefer a modern ARM64 Linux base image with a libc close enough to the host-bound CUDA libraries, because Apptainer `--nv` binds host NVIDIA libraries into the container and warns about libc mismatches ([Apptainer GPU support](https://apptainer.org/docs/user/main/gpu.html)).

### Apptainer execution checks on Vista

1. Start on `gh-dev` for a one-node smoke test because TACC documents `gh-dev` as the short development queue for Grace Hopper nodes ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)).
2. Run the container with `apptainer exec --nv` so `/dev/nvidia*` devices and matching host CUDA/NVIDIA libraries are available in the container ([Apptainer GPU support](https://apptainer.org/docs/user/main/gpu.html)).
3. Check that `nvidia-smi -L`, `/dev/nvidia0`, and ideally `/proc/driver/nvidia/gpus` are visible inside the container, because Genesis issue #2683 shows a current feature request for cases where containers expose device files but not `/proc/driver/nvidia/gpus` ([Genesis issue #2683](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2683); [Apptainer GPU support](https://apptainer.org/docs/user/main/gpu.html)).
4. Validate `torch.cuda.is_available()`, `torch.version.cuda`, `platform.machine()`, `import genesis as gs`, `gs.init(backend=gs.gpu)`, `scene.build()`, and one `scene.step()` before launching a long L2 run, because both TACC and Genesis issue history point to GPU/toolchain validation as the first failure point ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/); [Genesis discussion #2582](https://github.com/Genesis-Embodied-AI/genesis-world/discussions/2582)).
5. Avoid `--contain` or custom bind restrictions until Genesis GPU detection is confirmed, because issue #2683 shows that missing `/proc/driver/nvidia/gpus` can matter for Genesis’ current GPU-discovery path ([Genesis issue #2683](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2683)).

### MPM water + vehicle solver settings

1. Keep the MPM domain bounds tight around the channel, water, and vehicle path, because Genesis states domain size affects MPM performance and the solver raises when grid size exceeds `1e9` cells ([Genesis v1.2.0 MPMOptions](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/options/solvers.py); [Genesis v1.2.0 MPMSolver](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py)).
2. Treat `grid_density=64` as a coarse smoke-test value, then test `128` and possibly `256` near the final vehicle geometry, because issue #600 links MPM-rigid leakage to grid resolution and reports improvement at `grid_density=128` ([Genesis issue #600](https://github.com/Genesis-Embodied-AI/genesis-world/issues/600)).
3. Enable `enable_CPIC=True` for thin-object coupling tests, because Genesis v1.2.0 documents CPIC as supporting coupling with thin objects and defaults it to `False` ([Genesis v1.2.0 MPMOptions](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/options/solvers.py)).
4. Keep `substep_dt = dt / substeps` below the Genesis MPM suggested threshold `2e-2 * dx`, because the v1.2.0 solver warns that larger substep time steps may be unstable ([Genesis v1.2.0 MPMSolver](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py); [Genesis v1.2.0 Simulator](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/simulator.py)).
5. Use simple, watertight, untextured collision geometry for the vehicle and keep high-detail textured GLBs out of the physics path, because issue #2890 shows large host-memory regressions from many textured GLB submeshes ([Genesis issue #2890](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2890)).
6. Run forward-only `requires_grad=False` for production ford/no-ford sweeps unless gradients are scientifically required, because v1.2.0 uses extra memory in differentiable mode and issue #2865 shows a differentiable GPU contact path that produced missing contacts in one bug report ([Genesis v1.2.0 SimOptions](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/options/solvers.py); [Genesis issue #2865](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2865)).
7. Record a resolution-convergence table for the central case `d=0.30 m, v=1.5 m/s`, including lateral displacement/drag, leakage count or visible penetration, max water-particle speed, GPU memory, host memory, and wall time, because the confirmed Genesis risks are grid-resolution leakage and time-step instability rather than a documented GH200-specific physics bug ([Genesis issue #600](https://github.com/Genesis-Embodied-AI/genesis-world/issues/600); [Genesis v1.2.0 MPMSolver](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py)).

### GH200 memory and performance practices

1. Target runs that fit in the H200’s 96 GB HBM before relying on Grace Hopper unified-memory oversubscription, because Vista GH nodes provide 96 GB HBM3 plus CPU LPDDR and NVIDIA describes UVM oversubscription as possible but not free ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/); [NVIDIA GH200 memory blog](https://developer.nvidia.com/blog/simplify-system-memory-management-with-the-latest-nvidia-gh200-nvl2-enterprise-ra/)).
2. Treat unified-memory page migration as a performance risk rather than a guaranteed capacity win, because NVIDIA forum guidance warns that page-fault-driven migration can fetch pages in small chunks and recommends prefetching or structured allocation when possible ([NVIDIA Developer Forum: Grace Hopper unified memory performance](https://forums.developer.nvidia.com/t/performance-decrease-on-unified-gracehopperc/322208)).
3. Monitor both GPU and CPU memory during scaling tests, because Genesis’ MPM grid/particles allocate GPU-side fields while complex GLB assets can consume host RSS ([Genesis v1.2.0 MPMSolver](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py); [Genesis issue #2890](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2890)).
4. Disable viewers and expensive rendering in production simulation jobs, because renderer-related CUDA linking bugs and visual-asset memory regressions are separate from the core MPM physics signal ([Genesis issue #2814](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2814); [Genesis issue #2890](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2890)).
5. Use one Genesis physics process per GH node for initial L2 production runs and only consider MPS or multiple processes after profiling single-process GPU utilization, because TACC documents MPS as useful for underutilized multi-process workloads rather than as a default requirement ([TACC Vista MPS guide](https://docs.tacc.utexas.edu/hpc/vista/mps/)).

### Minimum Vista smoke-test checklist

- Platform check: `platform.machine()` should report ARM64/aarch64 behavior, because Vista’s Grace nodes are ARM-based ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/)).
- GPU check: `nvidia-smi -L` should see the H200 GPU inside `apptainer exec --nv`, because Apptainer `--nv` is responsible for exposing NVIDIA devices and libraries ([Apptainer GPU support](https://apptainer.org/docs/user/main/gpu.html)).
- PyTorch check: `torch.cuda.is_available()` should be true and `torch.version.cuda` should match the installed CUDA wheel family, because TACC and PyTorch ARM64 guidance emphasize explicit CUDA wheel selection ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/); [PyTorch issue #160162](https://github.com/pytorch/pytorch/issues/160162)).
- Genesis check: `genesis-world==1.2.0` and `quadrants==1.0.2` should be present, because v1.2.0’s dependency pin is the reproducibility anchor ([Genesis World v1.2.0 pyproject](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/pyproject.toml)).
- Physics check: a minimal MPM liquid + rigid obstacle scene should run for at least 100-500 steps at `grid_density=64`, then repeat at `128`, because issue #600 makes grid resolution the first confirmed MPM-rigid coupling risk ([Genesis issue #600](https://github.com/Genesis-Embodied-AI/genesis-world/issues/600)).
- Stability check: the production script should fail fast on NaNs, non-returning `scene.step()`, leakage-through-vehicle, and memory growth, because Genesis issues report NaNs, rigid GPU hangs, fluid leakage, and host-memory regressions in separate contexts ([Genesis issue #2652](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2652); [Genesis issue #2815](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2815); [Genesis issue #2319](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2319); [Genesis issue #2890](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2890)).

## Bottom line for “Can It Ford?”

The current evidence does **not** show a confirmed Genesis v1.2.0 bug specific to Vista GH200 or Apptainer, but it does show confirmed risks that can invalidate a ford/no-ford L2 result if left untested: ARM64 dependency selection, container GPU visibility, MPM-rigid leakage through under-resolved geometry, MPM time-step instability, visual-asset host-memory growth, and GH200 UVM performance degradation under oversubscription ([Genesis issue #2681](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2681); [Genesis issue #2683](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2683); [Genesis issue #600](https://github.com/Genesis-Embodied-AI/genesis-world/issues/600); [Genesis v1.2.0 MPMSolver](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py); [Genesis issue #2890](https://github.com/Genesis-Embodied-AI/genesis-world/issues/2890); [NVIDIA Developer Forum: Grace Hopper unified memory performance](https://forums.developer.nvidia.com/t/performance-decrease-on-unified-gracehopperc/322208)). The safest interpretation is that Vista GH200 is a plausible target for Genesis v1.2.0, but the scientifically defensible L2 ford/no-ford claim needs a small convergence-and-instrumentation campaign around the water-rigid coupling case, especially at the central divergence point `d=0.30 m, v=1.5 m/s` ([TACC Vista User Guide](https://docs.tacc.utexas.edu/hpc/vista/); [Genesis issue #600](https://github.com/Genesis-Embodied-AI/genesis-world/issues/600); [Genesis v1.2.0 MPMOptions](https://github.com/Genesis-Embodied-AI/genesis-world/blob/v1.2.0/genesis/options/solvers.py)).
# Genesis MPM Flood Simulation Parameters for “Can It Ford?”

## Executive recommendation

For the 4 m × 1 m × 1 m flooded-road domain, the most defensible starting point is Genesis `MPMOptions(grid_density=64, particle_size=None)` because Genesis v1.2.0 defines `grid_density` as “Number of grid cells per meter” with default 64 and auto-resolves the default MPM particle diameter to `0.01 * 64.0 / grid_density`, giving `dx = 1/64 = 0.015625 m` and `particle_size = 0.01 m` at the default setting ([Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L583-L620), [Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L35-L63)).

That setting resolves the shallowest target depth, 0.1 m, by about 6.4 grid cells and resolves 0.6 m by about 38.4 grid cells, while Genesis’s default particle diameter corresponds to about 3.81 particles per grid cell in 3D, which is close to the common 4 particles-per-cell baseline and below the 8 particles-per-cell “typical setting” noted in the multi-GPU MPM literature ([Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L583-L620), [Zhu et al. 2020](https://yzhu.io/publication/mpmgpu2020siggraph/paper.pdf)).

Genesis v1.2.0 explicitly warns when `substep_dt` exceeds `2e-2 * dx`, so `dx = 0.015625 m` implies `substep_dt <= 3.125e-4 s`; therefore use `dt=4e-3, substeps=16-20` for Genesis simulation steps, or about 64 substeps for a 60 Hz rendered/output frame ([Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L253-L259)).

At `particle_size = 0.01 m`, the water phase contains about 0.4 million particles at 0.1 m depth, 1.2 million at 0.3 m depth, and 2.4 million at 0.6 m depth; a fully volumetric MPM vehicle box of 1.5 m × 0.8 m × 0.6 m would add about 0.72 million particles at the same spacing, while a one-cell-thick shell proxy would add about 0.08 million particles ([Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L583-L620), [Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L45-L50)).

The resulting forward, non-differentiable Genesis run should fit comfortably in a 96 GB GH200 unified-memory allocation: a conventional MLS-MPM state estimate of 128 bytes/particle gives about 0.05-0.40 GB for the water particles alone across the 0.1-0.6 m depth range, while Genesis’s v1.2.0 allocated particle structs are closer to roughly 560 bytes/particle in forward mode once two dynamic frames, static info, render state, and flags are included, giving about 0.22-1.34 GB for water alone or about 1.75 GB for 2.4 million water particles plus a 0.72 million-particle volumetric vehicle ([Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L82-L150), [Zhu et al. 2020](https://yzhu.io/publication/mpmgpu2020siggraph/paper.pdf)).

## Section 2: Genesis official docs/GitHub defaults for MPM.Liquid

Genesis v1.2.0 defines `SimOptions.dt` with default `1e-2` seconds and `SimOptions.substeps` with default `1`, so a user who does not override these settings gets a 10 ms scene step and only one substep ([Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L17-L59)).

Genesis v1.2.0 defines `MPMOptions.dt` as optional and states that if `dt` is not set at the solver level, it inherits from `SimOptions` ([Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L579-L586), [Genesis MPMOptions documentation](https://genesis-world.readthedocs.io/en/latest/api_reference/options/simulator_coupler_and_solver_options/mpm_options.html)).

Genesis v1.2.0 defines `MPMOptions.grid_density` default as `64` cells per meter and `MPMOptions.particle_size` default as `None`, then resolves missing `particle_size` to `0.01 * 64.0 / grid_density` ([Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L583-L620)).

Genesis v1.2.0 computes the MPM grid spacing as `dx = 1.0 / grid_density`, computes grid resolution from rounded bounds, and rejects grids with more than `1e9` cells ([Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L35-L63)).

Genesis v1.2.0 adds a safety padding of `3 * dx` to the MPM boundary, so the active boundary is slightly tighter than the `lower_bound` and `upper_bound` values ([Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L74-L80)).

Genesis v1.2.0 emits a stability warning when `substep_dt` is greater than `2e-2 * dx`, using the exact warning text “Current `substep_dt` ... is greater than suggested_dt ... calculated based on `grid_density`. Simulation might be unstable” ([Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L253-L259)).

Genesis v1.2.0’s `MPM.Liquid` class documents `E = 1e6`, `nu = 0.2`, `rho = 1000 kg/m³`, and `viscous = False` defaults, and the non-viscous branch sets `mu = 0.0` and disables SVD need for liquid stress updates ([Genesis v1.2.0 `liquid.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/materials/MPM/liquid.py#L12-L38), [Genesis MPM Liquid documentation](https://genesis-world.readthedocs.io/en/latest/api_reference/material/mpm/liquid.html)).

Genesis v1.2.0’s MPM base material computes Lame parameters from `E` and `nu` when `lam` or `mu` is not provided, using `mu = E / (2 * (1 + nu))` and `lam = E * nu / ((1 + nu) * (1 - 2 * nu))` ([Genesis v1.2.0 `base.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/materials/MPM/base.py#L60-L85)).

For the Genesis default liquid values `E = 1e6` and `nu = 0.2`, the computed `lam` is about 277,778 Pa, and the non-viscous `MPM.Liquid` stress law uses `lam * J * (J - 1)` as the volumetric stress term ([Genesis v1.2.0 `base.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/materials/MPM/base.py#L60-L85), [Genesis v1.2.0 `liquid.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/materials/MPM/liquid.py#L48-L52)).

Genesis’s official MPM tutorial uses `dt = 4e-3`, `substeps = 10`, MPM bounds `(-0.5, -1.0, 0.0)` to `(0.5, 1.0, 1)`, and an entity with `material=gs.materials.MPM.Liquid()` ([Genesis beyond-rigid-bodies tutorial](https://genesis-world.readthedocs.io/en/latest/user_guide/getting_started/beyond_rigid_bodies.html), [Genesis v1.2.0 tutorial source](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/examples/tutorials/mpm.py#L9-L55)).

The Genesis v1.2.0 `flush_cubes.py` coupling example uses `dt = 4e-3`, `substeps = 20`, `grid_density = 64`, two `MPM.Liquid(sampler="random")` emitters, and `max_particles=800000` for each emitter ([Genesis v1.2.0 `flush_cubes.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/examples/coupling/flush_cubes.py#L17-L90)).

Genesis issue discussion on MPM-rigid coupling says MPM-rigid coupling uses the MPM grid for collision, advises making the grid smaller than the rigid object, and suggests increasing `grid_density` from 64 to 128 or 256 when particles pass through rigid bodies ([Genesis issue #600](https://github.com/Genesis-Embodied-AI/Genesis/issues/600)).

The spillway SPH paper states that real water sound speed would produce very small CFL timesteps, recommends an artificial sound speed at least 10 times the maximum bulk flow velocity, and reports an initial `10−5 s` timestep under CFL control ([Zhang et al. 2017/2018](https://eprints.whiterose.ac.uk/id/eprint/125204/3/water-09-00973.pdf)).

The MPM timestep paper by Fang et al. 2020 states that “time step restrictions depend on a characteristic simulation length scale, which is often the grid Δx for MPM,” and summarizes a sound-speed CFL restriction of the form `Δt = ν Δx / c`, with `ν ≤ 1` ([Fang et al. 2020](https://www.cs.ucr.edu/~craigs/papers/2020-sound-speed/paper.pdf)).

The same timestep paper also states that explicit MPM instability can arise from CFL violation and from isolated fluid-particle instability, so splashing and isolated water particles are a real stability concern in the vehicle-flood case ([Fang et al. 2020](https://www.cs.ucr.edu/~craigs/papers/2020-sound-speed/paper.pdf)).

## Section 4: Derived recommendation for this project

### Spatial grid and particle spacing

Use `grid_density = 64` for the main L2 parameter sweep, because it is the Genesis default, gives `dx = 0.015625 m`, and gives 6.4 cells across 0.1 m water depth, 19.2 cells across 0.3 m, and 38.4 cells across 0.6 m ([Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L583-L620), [Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L35-L63)).

Use the Genesis auto particle size at this setting, `particle_size = 0.01 m`, because it yields `ppc = (dx / particle_size)^3 = 3.81`, which is effectively a 4 particles-per-cell MPM discretization and matches the default relation documented by Genesis ([Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L583-L620)).

Use `grid_density = 96` or `128` only for a short verification run near the vehicle-water interface, because Genesis issue discussion indicates finer MPM grids can reduce rigid-body pass-through, but uniform 128 cells/m would roughly octuple grid cells and roughly double-to-triple particle counts depending on particle-size choice ([Genesis issue #600](https://github.com/Genesis-Embodied-AI/Genesis/issues/600), [Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L35-L63)).

### Timestep and substeps

For `grid_density = 64`, Genesis’s built-in warning threshold is `suggested_dt = 2e-2 * dx = 3.125e-4 s`, so `dt=4e-3` should use at least 13 substeps and should be rounded up to 16-20 substeps for safety ([Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L253-L259)).

For a 60 Hz output frame of `1/60 s`, the same Genesis threshold implies at least 54 substeps per rendered frame, so the practical implementation should either run about four `dt=4e-3` Genesis steps per rendered frame with 16-20 substeps each or set a 60 Hz scene step with about 64 substeps ([Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L253-L259)).

The advective CFL estimate for 2 m/s water speed is much looser, because `dx / vmax = 0.015625 / 2 = 7.8125e-3 s`, so stiffness/sound-speed and Genesis’s internal `2e-2 * dx` warning dominate rather than bulk advection ([Fang et al. 2020](https://www.cs.ucr.edu/~craigs/papers/2020-sound-speed/paper.pdf), [Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L253-L259)).

Genesis’s default liquid `lam ≈ 277,778 Pa` and `rho = 1000 kg/m³` imply a weak-compressible wave-speed scale of about `sqrt(lam/rho) = 16.7 m/s`, which is close to the SPH rule of thumb that artificial sound speed should be at least 10 times the maximum bulk velocity when `vmax = 2 m/s` ([Genesis v1.2.0 `base.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/materials/MPM/base.py#L60-L85), [Genesis v1.2.0 `liquid.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/materials/MPM/liquid.py#L12-L52), [Zhang et al. 2017/2018](https://eprints.whiterose.ac.uk/id/eprint/125204/3/water-09-00973.pdf)).

Do not use the physical water bulk modulus of about 2.2 GPa for this explicit MPM run, because the particle-method literature warns that real water sound speed makes CFL timesteps extremely small and because Genesis’s liquid default is intentionally much softer than real water ([Zhang et al. 2017/2018](https://eprints.whiterose.ac.uk/id/eprint/125204/3/water-09-00973.pdf), [Genesis v1.2.0 `liquid.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/materials/MPM/liquid.py#L12-L52)).

### Particle counts

At `particle_size = 0.01 m`, the water particle count estimate is `N = volume / particle_size^3`, so a 4 m × 1 m × 0.1 m water slab gives about 400,000 particles, a 0.3 m slab gives about 1.2 million particles, and a 0.6 m slab gives about 2.4 million particles ([Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L583-L620), [Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L45-L50)).

If the 1.5 m × 0.8 m × 0.6 m vehicle is represented as a fully volumetric MPM body with the same `0.01 m` particle spacing, it adds about `0.72 / 1e-6 = 720,000` particles; if it is represented as a one-cell-thick shell, the estimate is about 80,000 particles.

A practical phase-sweep case at 0.6 m depth plus a volumetric MPM vehicle is therefore about 3.1 million particles, which is smaller than the 3.8 million-particle LS-DYNA SPH vehicle-water case and far smaller than the 48.6 million-particle multi-GPU MPM dam-break case ([LS-DYNA Users Conference paper](https://lsdyna.ansys.com/wp-content/uploads/attachments/t4-1-f-sph-201.pdf), [Zhu et al. 2020](https://yzhu.io/publication/mpmgpu2020siggraph/paper.pdf)).

### Memory footprint on GH200 96 GB

A conventional MLS-MPM particle state with position, velocity, deformation gradient `F`, affine matrix `C`, mass, volume, and a few scalars is roughly 128 bytes per particle in float32, and Zhu et al. list similar particle attributes including mass, position, velocity, deformation gradient, initial volume, and affine matrix ([Zhu et al. 2020](https://yzhu.io/publication/mpmgpu2020siggraph/paper.pdf)).

Using the 128 bytes/particle conventional estimate, the water phase alone uses about 51 MB at 0.1 m depth, 154 MB at 0.3 m depth, and 307 MB at 0.6 m depth; including a fully volumetric vehicle at 0.6 m depth gives about 399 MB for particles alone.

Genesis v1.2.0 allocates dynamic particle fields for `pos`, `vel`, `C`, `F`, `F_tmp`, `U`, `V`, `S`, `actu`, and `Jp`, plus static info, active flags, and render state, so a forward-mode rough estimate is closer to 560 bytes/particle when `substeps_local = 1` and two particle frames are stored ([Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L82-L150), [Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L54-L59)).

Using the Genesis-forward estimate, water particles use about 0.22 GB at 0.1 m depth, 0.67 GB at 0.3 m depth, and 1.34 GB at 0.6 m depth; water plus a volumetric vehicle at 0.6 m depth uses about 1.75 GB.

The 4 m × 1 m × 1 m grid at 64 cells/m has approximately 257 × 65 × 65 = 1.09 million cells in Genesis’s inclusive grid indexing, and the grid field stores mass plus two velocity vectors per cell, so the base grid and dirty-cell bookkeeping are only on the order of tens of MB in non-differentiable forward mode ([Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L53-L63), [Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L138-L165)).

The overall forward-memory conclusion is that a single GH200 with 96 GB unified memory should fit the recommended 64 cells/m, 0.01 m particle-size simulations comfortably, and the likely bottleneck will be runtime and stability tuning rather than raw memory.

## Section 5: Caveats, risks, and stability warnings

The exact uploaded Space PDF named `Genesis World - Genesis 1.0.0 documentation.pdf` could not be located by the file-search tool in this run, so Section 1 relies on the tool result plus official public Genesis documentation rather than quotes from that uploaded PDF.

Genesis’s default `SimOptions(dt=1e-2, substeps=1)` is not a safe MPM flood setting at `grid_density=64`, because the implied `substep_dt = 0.01 s` exceeds Genesis’s own MPM suggested threshold of `3.125e-4 s` by a factor of 32 ([Genesis v1.2.0 `solvers.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/options/solvers.py#L17-L59), [Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L253-L259)).

The official Genesis MPM tutorial’s `dt=4e-3, substeps=10` gives `substep_dt=4e-4 s`, which is above the v1.2.0 `2e-2 * dx` warning threshold at default `grid_density=64`; the `flush_cubes.py` MPM-liquid coupling example’s `substeps=20` is therefore a better template for flooded-road runs ([Genesis v1.2.0 tutorial source](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/examples/tutorials/mpm.py#L9-L55), [Genesis v1.2.0 `flush_cubes.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/examples/coupling/flush_cubes.py#L17-L90), [Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L253-L259)).

Rigid coupling is a risk because Genesis issue discussion says MPM-rigid uses the MPM grid for collision and advises making the grid smaller than the rigid object, so under-resolved wheels, chassis edges, or road barriers can cause leakage or pass-through ([Genesis issue #600](https://github.com/Genesis-Embodied-AI/Genesis/issues/600)).

Weakly compressible water is not physically incompressible water, because the particle-method literature explicitly notes that using real water sound speed would make CFL timesteps very small, and Genesis’s default liquid stiffness produces a computational wave speed around 16.7 m/s rather than the physical acoustic speed of water ([Zhang et al. 2017/2018](https://eprints.whiterose.ac.uk/id/eprint/125204/3/water-09-00973.pdf), [Genesis v1.2.0 `liquid.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/materials/MPM/liquid.py#L12-L52)).

Isolated splashes and thin sheets may require smaller substeps or particle cleanup because explicit-MPM timestep theory identifies single-particle fluid instability as a distinct stability restriction beyond ordinary CFL ([Fang et al. 2020](https://www.cs.ucr.edu/~craigs/papers/2020-sound-speed/paper.pdf)).

A one-cell-thick 0.1 m flood layer has only about six grid cells of depth at `grid_density=64`, so report any conclusion near the L0 depth threshold as resolution-sensitive and verify a few critical cases at 96 or 128 cells/m if GH200 runtime allows ([Genesis v1.2.0 `mpm_solver.py`](https://github.com/Genesis-Embodied-AI/Genesis/blob/v1.2.0/genesis/engine/solvers/mpm_solver.py#L53-L63), [Genesis issue #600](https://github.com/Genesis-Embodied-AI/Genesis/issues/600)).

The recommended settings are immediately runnable on Vista/GH200 in a Genesis container, while MacBook runs should stay at toy scale or use Taichi-only demos because the uploaded project context notes state that full Genesis L2 simulations are Vista jobs and MacBook Genesis/Taichi mixed imports can conflict ([uploaded project context note](https://ppl-ai-file-upload.s3.amazonaws.com/web/direct-files/collection_2211ba55-4b80-49a3-87ca-64f0de49d1c6/fbeb21ba-8602-4ccb-bc5a-ffb6f36fab12/claude_context_complete.md?AWSAccessKeyId=ASIA2F3EMEYEUSHCT3K6&Signature=Fg4C7PjNjmWRXS3ivFPCz3%2B98Z8%3D&x-amz-security-token=IQoJb3JpZ2luX2VjEJ3%2F%2F%2F%2F%2F%2F%2F%2F%2F%2FwEaCXVzLWVhc3QtMSJHMEUCIQCFrUEimRRlVL8Tcljyhj8dwVCpUvy4XfwJZuva6ceXdgIgPShl2cu6z6lCKf6Ftl0ehnDqJAajx0EYErUAeO4%2F6Fcq8wQIZhABGgw2OTk3NTMzMDk3MDUiDGa7NiFKdMNfdBWI2CrQBE2vDbShVwN%2BsdhgkmvX3GqtOhEEr8E%2BN2lnvb1jwHWZhNj015RjGS3FWRt%2FoZWyq7eLMxZWbbsRUxoHHWWeEud2UNjzbIOjV2barZuYcEg0zzjgNR2SRJdO9LsOe%2BvXFXpHLpPhnx7jCYvfz2LpAKUOX5pFjfTDvoSmUKUqSWNFDBbW25Io%2F67OHwE2Ku%2FiPs3IDacMGwH4%2F00H9ykxr%2Bd1sqVbPOw5jCKUASExkBswDRapQt2lQfVdaVFD4xtaTbFqGTPMUMXtU9ZYnUREGVY5Z485wMGE54m0mpMKwCyZg4l9OJPi0ErOhXoM%2Fwr1ctKdclTL3fzUsxNkZCbSsVOfG30rGlm6Q0xb0Gm78wM5uCrCAF4Pq%2F3LphQhq7RmBPPfc%2BKh9hfTYLPePcGUPfcTuhbUBPp13PtXIP9xRhpPGNoYWri8kGeue1YL5EJLu567bHiZqtn%2BxzpSNL7wSqFbFzaynLONBTnDm5OPaU3QxruT4hUJIfxdjIYtss4%2FOU9dAKSFJeChwcsdm6bkhJBZce%2F03bxsRjThewr28UfiAVtuSBrkkGUIEw2QcTtmBc2vpNinTxGOvDcK4a3zlNGQ9y8M7iDHhN7uqXTjpKIZZhthj0dkGtekt0xt78jwSC2Eu%2Bka%2BEn2ZoDnNfnYpaBjOcV%2FVLbNI0ZoRJt4DXQLa%2F0WdTk4cqKw09ii%2F9fx07oDdlHo6hu3mJlW1bBPBCmzBe8gjm1Z3G8wYFN7GOroJMVlh6%2BRiZ%2Bxru53Mmu%2F3TP7ZgqO8fcK17fUVJ%2B9TEkw%2BoSy0gY6mAEv%2FYOXwVXFjjPj32qJHa%2FzqnLRRNFD3cP5U43XX6zCcFY%2BnWWf7Pl0aMkYVub8pYO8WdQoBN30ygaYxZP6Dpqpo%2FMyOzddvXbsDBMBLdW%2BVFvS8pTRxhe4beQ0LM5fuTat8nzt0SlOC%2BTK9J9n5T9U%2F8pcxqdgbHMnW6Zr4%2FdcGChJVkjjjD4wo0z1qXL6iIkqVHwit0utdQ%3D%3D&Expires=1783402573)).

## 1. Stable solver parameters for the inspected kks32 engine and Taichi MLS-MPM cross-checks

### What the kks32 repository implies

The current `kks32/mpm-engine` high-level solver defines `GridConfig(n_grid=64, grid_lim=0.4)` and computes `dx = grid_lim / n_grid`, while the low-level Warp model explicitly comments that the domain is `[0, grid_lim]^3` in all three directions ([kks32 `GridConfig`](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/core/solver.py#L47-L55), [kks32 low-level grid initialization](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/kernels/mpm_solver_warp.py#L120-L136)). For a 2.5 m-long Can It Ford domain, that means `grid_lim` should be set to at least the longest physical dimension plus boundary/contact padding, e.g. `grid_lim=2.8–3.0`, with `n_grid=192–288` for 64–96 cells/m; otherwise particles near the boundary can trigger the repository's out-of-bounds guard ([kks32 active grid guard](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/core/solver.py#L369-L386)).

The `Solver.step(dt, substeps)` implementation passes the same `dt` to each MPM substep and loops over `substeps`, so in this repository `dt` should be interpreted as the **substep** time step rather than the rendered-frame time step ([kks32 `Solver.step`](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/core/solver.py#L313-L336)). The repository's own `pour_glass.py` example uses `n_grid=64`, `grid_lim=0.4`, `dx=6.25 mm`, `dt=1.5e-4`, `substeps=6`, `density=1000`, `bulk=2.0e5`, and `eta=4.0`, but this is a viscous pour example rather than real water because `eta=4 Pa·s` is honey-like compared with water ([kks32 `pour_glass.py`](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/examples/pour_glass.py#L45-L72)). The README performance note reports a 192³ honey pour with 340k particles and 432 substeps per frame on GH200, which supports planning for hundreds of substeps per output frame in production GPU runs rather than expecting 10–20 substeps to be enough at meter scale ([kks32 README performance note](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/README.md#L57-L57)).

### Recommended values for this domain

Use `grid_lim=3.0 m` and one of the following starting points:

| Purpose | Concrete config | Reasoning |
|---|---|---|
| Fast smoke test | `n_grid=128`, `grid_lim=3.0`, `dx=23.4 mm`, 4–8 PPC, `dt_sub≈1.8e-4–2.5e-4 s`, output every 50–100 substeps | Checks geometry, initial velocities, material wiring, and SDF/box collisions; 0.1 m water depth has only about 4 cells, so not a validation run. |
| Main B1 case | `n_grid=192`, `grid_lim=3.0`, `dx=15.625 mm`, 8 PPC, `dt_sub≈1.0e-4–1.2e-4 s`, output every 100–150 substeps for 60 Hz-like snapshots | Resolves 0.1 m depth by about 6.4 cells and 0.3 m depth by about 19 cells; particle counts are large but feasible on Vista GH200/LS6 A100. |
| Higher-resolution B1 case | `n_grid=256–288`, `grid_lim=3.0`, `dx=11.7–10.4 mm`, 8 PPC, `dt_sub≈0.8e-4–0.9e-4 s`, output every 190–220 substeps for 60 Hz-like snapshots | Better for shallow 0.1 m water, wake/vehicle contact, and convergence checks; cluster time required. |
| Convergence spot check | `n_grid=384`, `grid_lim=3.0`, `dx=7.8125 mm`, 8 PPC initially, 16 PPC if particle noise dominates | Expensive; use only for a few selected \\(d,v\\) cases and compare vehicle displacement/force histories against the main grid. |

Represent the vehicle as a rigid box/SDF/collider if possible rather than a volumetric MPM particle block, because an 8-PPC volumetric box at 64–96 cells/m can add millions of particles; this follows the repository's emphasis on collider/SDF workflows and wrench readouts rather than always representing rigid objects as material particles ([kks32 README solver features](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/README.md#L22-L35), [kks32 `solver.py` wrench methods](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/core/solver.py#L300-L307)).

### Taichi and MLS-MPM sanity checks

The Taichi 88-line MPM example uses a unit square with `n_grid = 128`, `dx = 1 / n_grid`, `dt = 2e-4`, and 50 substeps per GUI frame, which is consistent with the idea that explicit MPM examples use small substep timesteps and many substeps per rendered frame ([Taichi `mpm88.py`](https://raw.githubusercontent.com/taichi-dev/taichi/master/python/taichi/examples/simulation/mpm88.py)). The original MLS-MPM 88-line C++ reference uses `n = 80`, `dx = 1/n`, `dt = 1e-4`, and `frame_dt = 1e-3`, so it advances about 10 substeps per 1 ms output frame, and its high-quality advice reduces `dt` to `1e-5` when resolution is raised to `n = 320` ([MLS-MPM 88-line C++](https://raw.githubusercontent.com/yuanming-hu/taichi_mpm/master/mls-mpm88.cpp), [Taichi MLS-MPM README](https://raw.githubusercontent.com/yuanming-hu/taichi_mpm/master/README.md)). Hu et al. introduced MLS-MPM with two-way rigid-body coupling and CPIC, and the paper is the closest conceptual ancestor for Taichi-style MPM codebases even though the inspected `kks32/mpm-engine` current head is Warp-based rather than Taichi-based (Hu et al. 2018, DOI: [10.1145/3197517.3201293](https://dl.acm.org/doi/10.1145/3197517.3201293)).

## 2. CFL condition and worked safe-
`dt` formula

For explicit weakly-compressible MPM, use the conservative combined wave/flow bound

\[
\Delta t_{sub} \le C_{CFL}\,\frac{\Delta x}{c + \lVert v \rVert_{max}},
\]

where \\(\Delta x\\) is grid spacing, \\(\lVert v \rVert_{max}\\) is the expected maximum particle/grid velocity, \\(c\\) is the artificial acoustic speed for weakly-compressible water, and \\(C_{CFL}\\) should be about 0.2–0.4 for conservative production runs. Sun, Shinar, and Schroeder give the explicit MPM sound-speed CFL form \\(\Delta t = \nu\Delta x/c\\), with \\(\nu \le 1\\), and also recommend velocity, particle-displacement, deformation-gradient, collision, and single-particle fluid restrictions rather than relying on sound speed alone (Sun et al. 2020, DOI: [10.1111/cgf.14101](https://dl.acm.org/doi/10.1111/cgf.14101); [author PDF](https://www.cs.ucr.edu/~craigs/papers/2020-sound-speed/paper.pdf)). The common weakly-compressible particle-method rule is to choose an artificial sound speed at least 10 times the maximum flow velocity so that the Mach number is at or below about 0.1, keeping density fluctuations small (Lind et al. 2020, DOI: [10.1098/rspa.2019.0801](https://pmc.ncbi.nlm.nih.gov/articles/PMC7544338/); Monaghan 2012, DOI: [10.1146/annurev-fluid-120710-101220](https://www.annualreviews.org/content/journals/10.1146/annurev-fluid-120710-101220); Violeau and Rogers 2016, DOI: [10.1080/00221686.2015.1119209](https://www.tandfonline.com/doi/full/10.1080/00221686.2015.1119209)).

For the Can It Ford velocity range, choose \\(c = 10v_{max} = 30\\) m/s for \\(v_{max}=3\\) m/s. In the inspected kks32 Newtonian material, the default `bulk_modulus=9.0e5` and `density=1000` imply an acoustic scale near \\(\sqrt{K/\rho} = 30\\) m/s, and the source uses an EOS-style pressure term in the Newtonian stress update ([kks32 material defaults](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/materials/__init__.py#L26-L35), [kks32 Newtonian stress](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/kernels/mpm_utils.py#L28-L51)). Because the kks32 pressure law uses `gamma = 1.1`, the small-compression tangent acoustic speed is closer to \\(\sqrt{\gamma K/\rho}\\), so `bulk_modulus=9.0e5` gives about 31.5 m/s and is a good default for the 3 m/s upper-flow case ([kks32 Newtonian EOS code](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/kernels/mpm_utils.py#L28-L51)).

Worked example for `grid_lim=3.0`, `n_grid=192`, `dx=3.0/192=0.015625 m`, `v_max=3 m/s`, `c=30 m/s`, and `C_CFL=0.25`:

\[
\Delta t_{sub} \le 0.25\frac{0.015625}{30+3} = 1.18\times10^{-4}\;\mathrm{s}.
\]

A 60 Hz visualization interval is \\(1/60 = 0.01667\\) s, so the corresponding number of substeps is \\(\lceil 0.01667 / 1.18\times10^{-4}\rceil = 141\\). If the output interval is 30 Hz, the same substep requires about 282 substeps per output frame, and this is not surprising because the kks32 README reports hundreds of substeps per frame for a GH200 honey-pour benchmark ([kks32 README performance note](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/README.md#L57-L57)).

A practical guard is to enforce both the acoustic CFL rule above and a particle displacement rule such as \\(\lVert v\rVert_{max}\Delta t_{sub} \le 0.25\Delta x\\) for production runs; Sun et al. explicitly include a particle-displacement limit in which particle movement is kept below a grid-cell fraction, and the kks32 low-level code contains a commented diagnostic expressing the simpler check `v*dt > dx` as a nonphysical condition to avoid (Sun et al. 2020, DOI: [10.1111/cgf.14101](https://dl.acm.org/doi/10.1111/cgf.14101); [kks32 low-level solver](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/kernels/mpm_solver_warp.py)).

## 4. Newtonian-fluid units and water values in `newtonian(eta, density)`

Real water near 20 °C has dynamic viscosity about `1.0e-3 Pa·s` and density about `998 kg/m³`; NIST reports a standard water viscosity at 20 °C and 0.101325 MPa of `1.0016 mPa·s`, and the prior SPH verification notes use the standard engineering values `rho0=1000 kg/m³` and `mu=1e-3 Pa·s` for water (NIST/IAPWS report via [NIST](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=50047); Lind et al. 2020, DOI: [10.1098/rspa.2019.0801](https://pmc.ncbi.nlm.nih.gov/articles/PMC7544338/)). For the kks32 API, the physically literal call for water should therefore start as:

```python
from warpmpm.materials import newtonian
mat = newtonian(eta=1.0e-3, density=998.0, bulk_modulus=9.0e5)
```

The function signature in the inspected source is `newtonian(eta: float = 0.0, density: float = 1000.0, bulk_modulus: float = 9.0e5, E=1e5, nu=0.3)`, and the `Material` dataclass labels `viscosity` as `eta [Pa.s]`, `density` as `1000.0` by default, and the material as a weakly-compressible generalized-Newtonian fluid with EOS plus `2 eta dev D` ([kks32 material source](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/materials/__init__.py#L26-L35), [kks32 `newtonian` function](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/materials/__init__.py#L111-L116)). The low-level solver updates particle mass as `density * volume` when a density parameter is supplied, and the high-level solver injects gravity as `[0, 0, -9.81]`, which together imply SI-like units if positions are meters and times are seconds ([kks32 density-to-mass update](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/kernels/mpm_solver_warp.py#L456-L595), [kks32 material setter](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/core/solver.py#L153-L164)).

The important caveat is that `bulk_modulus` should **not** be set to real water's physical bulk modulus of about 2.2 GPa for these explicit weakly-compressible runs, because that would make \\(c\\) about 1480 m/s and force \\(\Delta t\\) down by roughly 50 times. Instead, choose an artificial weak-compressibility bulk modulus that gives \\(c \approx 10v_{max}\\), e.g. `bulk_modulus≈9e5 Pa` for `rho≈1000 kg/m³` and `v_max=3 m/s`, consistent with both the kks32 default and weakly-compressible particle-method practice (Lind et al. 2020, DOI: [10.1098/rspa.2019.0801](https://pmc.ncbi.nlm.nih.gov/articles/PMC7544338/); [kks32 material defaults](https://github.com/kks32/mpm-engine/blob/2ff9caf547b62a9bca36385a05659a4184ee5a16/src/warpmpm/materials/__init__.py#L26-L35)). If real-water viscosity creates noisy or under-damped free-surface behavior, run a sensitivity set with `eta=1e-2–1e-1 Pa·s` and label it as numerical/regularization viscosity rather than as physical water.

## Bottom-line B1 parameter set

The most defensible first production configuration is `grid_lim=3.0`, `n_grid=192`, `dx=15.625 mm`, `newtonian(eta=1e-3, density=998, bulk_modulus=9e5)`, 8 PPC seeded by `h=dx/2`, `dt_sub=1.0e-4–1.2e-4 s`, and about 140–170 substeps per 60 Hz output interval. The first convergence upgrade should be `n_grid=256–288` at the same `grid_lim`, with `dt_sub≈0.8e-4 s`, because it improves shallow-depth and obstacle-contact resolution without immediately jumping to the 33M-particle worst case implied by 128 cells/m at 1 m water depth.
